Dalam membuat
use case diagram
, hubungan antar-lingkaran (fitur) sering kali membutuhkan relasi tambahan bernama
«include»
dan
«extend»
(bukan
exclude
).
Berikut adalah panduan teknis yang mudah dipahami beserta visualisasinya menggunakan contoh sistem tiruan Halodoc Anda.
1.
«include»
(Hubungan yang Wajib)
«include»
digunakan jika sebuah
use case
utama
pasti dan wajib
menjalankan
use case
lain di dalamnya agar bisa selesai. Tanpa fungsi tambahan itu, fungsi utama tidak akan bisa berjalan.
Arah Panah:
Dari
use case
utama
menunjuk ke
use case
wajibnya (
Utama ➔ Wajib
).
Contoh Halodoc:
Saat pasien ingin
"Melakukan Konsultasi"
, sistem
wajib
melakukan
"Verifikasi Pembayaran"
terlebih dahulu. Konsultasi tidak akan pernah terjadi jika pembayaran belum diverifikasi.
Gambarannya:
[Melakukan Konsultasi]
-------
«include»
------->
[Verifikasi Pembayaran]
2.
«extend»
(Hubungan Opsional / Kondisional)
«extend»
digunakan jika sebuah
use case
tambahan
hanya akan berjalan dalam kondisi tertentu
atau sifatnya opsional (pilihan). Fungsi utama tetap bisa selesai meski fungsi tambahan ini tidak dijalankan.
Arah Panah:
Dari
use case
opsional
menunjuk ke
use case
utamanya (
Opsional ➔ Utama
).
Catatan: Ini sering terbalik, ingat bahwa panah extend menunjuk ke arah induknya.
Contoh Halodoc:
Saat pasien sedang
"Melakukan Konsultasi"
, dokter mungkin akan
"Membuat Resep Digital"
, tetapi
hanya jika
pasien memang butuh obat. Jika pasien hanya butuh saran medis, resep tidak akan dibuat.
Gambarannya:
[Membuat Resep Digital]
-------
«extend»
------->
[Melakukan Konsultasi]
Rangkuman Perbedaan (Biar Mudah Ingat)
Fitur
«include»
«extend»
Sifat
Wajib
terjadi
Opsional
(Tergantung situasi)
Contoh
Konsultasi
pasti
butuh Pembayaran.
Konsultasi

menghasilkan Resep Obat.
Arah Panah
Menunjuk ke fitur yang
dibutuhkan
.
Menunjuk ke fitur
utama / induk
.

Dalam sistem medis seperti Halodoc, data medis pasien sifatnya sangat rahasia (
confidential

use case
-nya diatur seperti ini:
1. Apa yang BISA dikelola Admin (Dimasukkan ke Use Case)
Admin mengelola akun pasien dari sisi administratif atau teknis sistem, bukan rekam medisnya.
Memblokir Akun Pasien
: Jika pasien melakukan penipuan atau melanggar ketentuan.
Melihat Data Profil Dasar
: Nama, nomor telepon, dan email untuk kebutuhan
customer service
jika pasien komplain masalah akun.
Maka, Anda bisa menambahkan
usecase
baru untuk Admin:
[Mengelola Data Akun Pasien]
.
2. Apa yang TIDAK BISA dikelola Admin (Jangan Dimasukkan)
Admin
tidak boleh
melihat atau mengelola riwayat obrolan
chat
, keluhan penyakit, atau rekam medis pasien. Fungsi melihat penyakit dan memberikan resep itu sepenuhnya adalah hak
use case
milik
Dokter
.
Perbedaan Teknis
[Mengelola Data Dokter]
vs
[Mengelola Data Pasien]
Untuk memperjelas diagram Anda nanti, ini perbedaan cara kerja Admin untuk kedua aktor tersebut:
Untuk Dokter:
Admin bertindak sebagai
Gatekeeper
(Penjaga gerbang). Admin harus memverifikasi STR (Surat Tanda Registrasi) dan ijazah dokter sebelum mereka boleh melayani pasien. (Admin aktif mengurusi data dokter).
Untuk Pasien:
Pasien bisa langsung masuk dan menggunakan sistem setelah registrasi mandiri. Admin baru turun tangan mengelola data pasien jika ada masalah akun atau pelanggaran. (Admin pasif/hanya memantau).

use case diagram

Anda terlihat profesional dan langsung disetujui dosen/klien:
1. Trik Penamaan: Gunakan Rumus "Kata Kerja + Objek"
Setiap nama di dalam lingkaran
use case
harus diawali dengan kata kerja aktif untuk menunjukkan aksi yang menghasilkan tujuan.
❌
Salah (Nama Benda):

,
[Data Dokter]
,
[Form Login]
vv
Benar (Aksi):
[Melakukan Konsultasi]
,
[Mengelola Data Dokter]
,
[Melakukan Login]
2. Trik Menentukan Aktor: Bukan Berdasarkan Jabatan, Tapi "Peran"
Aktor di UML melambangkan peran (
role
) seseorang saat berinteraksi dengan sistem, bukan nama jabatan di dunia nyata.
Jika seorang Dokter di aplikasi Halodoc Anda tiba-tiba ingin berkonsultasi sebagai pasien dengan dokter lain, maka saat itu dia bertindak sebagai aktor
Pasien
.

Sistem Payment Gateway

Selalu gambar kotak besar yang membungkus semua lingkaran
usecase
Anda. Kotak ini disebut
System Boundary

Di dalam kotak:
Semua fungsi/lingkaran sistem (aplikasi Halodoc Anda).
Di luar kotak:
Semua aktor (manusia atau sistem luar).
Trik ini sering lupa digambar, padahal ini penanda batas apa yang Anda buat dan apa yang tidak.
4. Trik Menghindari "Mati Kena Spageti" (Garis Menyilang)
Jika aplikasi memiliki banyak fitur, garis relasi antara aktor dan lingkaran akan saling bertabrakan seperti mi spageti.
Solusinya:
Urutkan lingkaran
usecase
dari atas ke bawah berdasarkan alur penggunaan (misal: urutan atas adalah
[Registrasi]

[Login]
, tengah
[Konsultasi]
, bawah
[Melihat Laporan]

Tanyakan ini pada diri sendiri saat membuat lingkaran baru:
"Apakah fungsi ini memberikan hasil akhir yang jelas bagi aktor?"
[Memasukkan Password]

Karena proyek clone Halodoc ini diminta oleh atasan untuk proyek serius, Anda wajib memahami dua istilah ini agar bisa menjelaskannya dengan percaya diri saat presentasi. Berikut penjelasan mudahnya:
1. Apa itu Snap Token Transaksi?
Snap Token
adalah sebuah "kode tiket unik" (berupa kombinasi huruf dan angka acak) yang dibuat oleh server
payment gateway
atas permintaan sistem aplikasi Anda.
Bagaimana cara kerjanya?
Saat pasien mengklik "Bayar", sistem Anda akan mengirim data (contoh:
Total Bayar Rp50.000
) ke Midtrans. Midtrans lalu membuatkan satu
Snap Token
khusus untuk transaksi tersebut.
Untuk apa gunanya?
Token inilah yang digunakan untuk
memunculkan halaman pembayaran aman
(yang berisi pilihan klik bayar pakai GOPAY, QRIS, BCA Virtual Account, dll) di layar HP pasien. Tanpa Snap Token, halaman pilihan pembayaran itu tidak akan bisa terbuka.
2. Apa itu Status Callback ke Sistem?
Callback
(sering juga disebut
Webhook
) adalah
surat notifikasi otomatis
dari server
payment gateway
yang dikirimkan langsung ke database sistem Anda untuk mengabarkan hasil akhir transaksi.
Mengapa ini sangat penting?
Saat pasien melakukan transfer di aplikasi m-banking mereka, yang tahu uangnya sudah masuk atau belum adalah pihak bank/
payment gateway
, bukan aplikasi Halodoc Anda.
Bagaimana cara kerjanya?
Begitu uang ditransfer oleh pasien, server
payment gateway
akan mendeteksi uang tersebut, lalu mereka secara otomatis memanggil URL server Anda (
Callback
) untuk memberikan laporan:
"Halo Sistem Halodoc, transaksi dengan token X sudah
Sukses
dibayar!"
atau
"Transaksi token Y sudah
Expired/Gagal
karena lewat batas waktu."
Hasil Akhirnya:
Berdasarkan surat
Callback
itulah sistem Anda tahu kapan harus mengubah status di aplikasi menjadi berhasil dan otomatis memicu kotak
Terbitkan Tiket Konsultasi
.
Kesimpulan untuk Bahan Presentasi ke Atasan:
"Sistem kita tidak menyimpan atau memproses data kartu kredit/rekening bank pasien secara langsung demi keamanan. Kita menggunakan teknologi
Snap Token
untuk memunculkan gerbang pembayaran pihak ketiga yang aman, dan memanfaatkan fitur
Callback
agar sistem kita langsung tahu secara
real-time
ketika pembayaran pasien sudah sukses didebit oleh bank."
